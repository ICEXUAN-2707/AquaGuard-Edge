## 审查发现（按优先级）

### P1：容量检查早于时间推进，过期缓存可阻塞新消息
位置 src/stream.py:58-60。capacity=1，1 秒输入一条，再 push 100 秒新消息，直接报满；实际上先发布到期窗口并清理后可容纳。这会使依赖 push 推进时钟的调用方持续无法恢复。建议原子预计算截止输出与清理结果，再决定容量；必须保证失败不会丢窗口，并补“缓冲满后长时间沉默再输入”回归。

### P1：启动周期切换缺少输入资格检查
位置 src/stream.py:63-67 与 src/alignment.py:57。未来时间的新 boot 消息仍先清空旧状态、退役旧 boot；窗口算法才过滤其异常时间。最小复现：water 在 25 秒为 wet，26 秒收到 boot=b 但 event_time=100 秒，water 随后为 unknown，boot=a 已退役。应明确无效时间或未知新 boot 是否有权改变设备周期；将周期证据验证置于状态变更前。未证明 boot 可信时仅靠首次出现字符串不足以识别最新启动。

### P1：advance 单次输出不受限
位置 src/stream.py:30。大时间跳跃按步长循环并积累所有窗口，输入缓冲容量不能限制返回列表内存或阻塞时长。建议每次最多发布 N 窗，返回追赶游标；还需设计 push 在追赶未结束时的接收规则，避免跳过旧窗口。

### P2：算法语义版本与配置版本混合
位置 src/alignment.py:39。版本前缀仍是 sp03-r02，摘要只包含参数；实现逻辑变更可能复用 window_id。建议加入明确算法语义版本，并单独记录输入、代码版本或哈希，历史 evidence 保持不覆盖。

### P2：窗口时钟调用顺序仍由调用者保证
先 advance 到 32 秒，再输入 received_at=32 的消息，被允许但成为发布后迟到；先输入再 advance 则纳入。已有文档规定顺序，因此属于已知接口约束；正式入口建议以同时间批次 API 强制执行，或明确拒绝已经封闭时刻的新输入。

### P2：可复现证据与可维护性仍需加强
目前黄金输入少、三源综合长序列不足；尚无持久化恢复、时钟映射和负载实验。tests 互相导入帮助函数，data/build_case.py 也依赖测试模块；建议将 fixture 构造移入独立工具，避免数据生成依赖 pytest。replay 使用宽 DTO，alignment 使用更严格 raw 校验，两入口质量接受范围需要统一或明确差异。

## 已知实验取舍（不是本轮新发现的缺陷）
flow 时间戳按区间终点、窗尾无新间隔即 unknown；重启清空整窗历史覆盖；seq 暂按源级；实际发布延迟未测量；published_at 是逻辑截止而非真实服务发送时间；无硬件时钟与 MQTT 实测。以上均需口径评审，不可以结构测试代替。

## 证据与测试缺口
- evidence/stage_review_tests.txt：现有回归输出。
- evidence/stage_review_reproduce.py 与 .json：容量、启动和截止顺序最小复现。
- 复现输入完全合成；问题复现不是现有测试失败，说明现有测试覆盖不足。

## 建议整改顺序
1. 修复容量与过期清理的操作顺序并保证失败原子性。
2. 明确并实现新 boot 的资格规则，补异常时间与延迟旧周期场景。
3. 限制单次窗口输出并验证追赶时序。
4. 固定算法语义版本、统一输入质量校验、扩充三源黄金数据。
5. 完成独立 Reviewer 检查和 A/B/C 口径确认后，判定模拟 SP-03 是否退出，再进入 M4。
