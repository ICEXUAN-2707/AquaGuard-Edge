# 第 3 轮报告｜分源 TTL、流式时钟和重启隔离

日期：2026-10-29。状态 PARTIAL：本轮原型验证通过，完整 SP-03 仍待独立复核和硬件时间语义验证。synthetic / prototype_only。

## 组会讲解
第一轮建立统一输入和回放；第二轮验证固定截止窗口；第三轮让窗口引擎可以由外部时钟持续推进，并补上不同传感器的有效期、设备重启隔离与缓存保护。没有消息也能发布窗口，旧设备状态不会跨重启继续被当作新鲜读数。我们用测试核对了同启动周期的离线与流式窗口结果。

## 开发内容和思路
- alignment.py 新增三源 TTL 配置，要求完整且均为正数，配置参与版本摘要。
- stream.py 新增 Stream：明确 device_id、首个窗口结束时间、步长、容量和启动历史上限。push 输入消息；advance 显式推进时钟并返回应发布窗口。
- 截止相等时，先 push 完该时间戳的全部消息，再 advance；push 自动发布严格早于消息到达时间的窗口。调用者必须遵守此顺序。
- 返回窗口和审计包交给调用者保存，不在引擎里无限积累；历史输入按窗口长度与最大 TTL 保守清理。
- 缓存满时明确拒绝输入，不静默丢样；启动历史满时也拒绝新启动周期，需要显式结束实验。该策略保证有界，不保证过载时持续可用。
- 首次见新 boot 时清空旧读数、记录 BOOT_RESET；已退役 boot 的延迟消息拒绝。假定 boot_id 设备级、唯一且可靠，首次识别新 boot 的时间是接收时间，不能推断真实重启时刻。

## Review、修复及交叉检查
- 代码自查发现浅拷贝会让调用者后续修改输入值影响缓存，已改为深拷贝，并新增回归测试。
- 补上 BOOT_RESET 可审计记录与对应断言。
- 独立手算分源 TTL：water 在 25 秒观测，有效期 3 秒，30 秒窗尾未知，覆盖 3/30。
- 同一 boot 的相同消息/截止时钟，批处理与流式逐窗口字段完全一致；这是限定场景的一致性验证，不代表所有输入已证明等价。

## 限制与下一轮
1. 重启清空整个缓存为保守实验方案，会丢失窗口内重启前有效覆盖；不能当作精确跨启动周期时间重建。离线 align 本身不做重启隔离，生产入口必须使用明确策略。
2. 输入需按接收时间提交；退役 boot 拒绝，不支持任意跨启动周期重排。时钟同步、漂移和 uptime 映射尚无实物证据。
3. flow 时间戳仍假定统计间隔终点；flow 的终态采用第二轮保守口径，待联合确认。
4. 超大时间跳跃会返回大量窗口，单次返回列表尚未分批限制；缓存有界不等于整个进程在任意调用下内存均有界。
5. 没有持久化检查点、进程崩溃恢复或真实 MQTT 性能结论；这些能力不得标为完成。
6. 下一轮先补完整 SP-03 场景矩阵和逐窗口黄金输出，评审 flow 端点、重启覆盖语义和时钟降级，再进入 M4 特征开发。
