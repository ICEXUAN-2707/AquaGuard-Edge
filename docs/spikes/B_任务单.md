# B 组员任务单

## 你负责什么

你负责 SP-03 和 SP-04，回答两个问题：不同时间到达的传感消息能否形成确定、可重复的窗口；规则或轻量模型是否比简单基线更有用。

**先做 SP-03，确认窗口输出后再做 SP-04。** 开始阶段使用合成数据即可。当前可参考 [V1.2 候选规范](../../reference/reference_02/00_Contracts_V1.2_修订候选.md)，但 C0 会签仍待完成；Spike 数据标为 `prototype_only`，只能用于独立实验，不能据此认定正式合同已冻结。

## 开始前先做

1. 请组长给你分配 SP-03、SP-04 的 Issue、分支和 Reviewer。Owner 不能自己验收。
2. 查看 [Spike Issue 模板](templates/SPIKE_ISSUE_TEMPLATE.md) 和 [Spike 报告模板](templates/SPIKE_REPORT_TEMPLATE.md)，分别建 `spikes/SP-03/`、`spikes/SP-04/`。
3. 使用 A 提供的模拟消息时，保留 A 的原始文件；若 A 的文件未准备好，先自己造小型 CSV/JSONL，在文件名、README、报告或 sidecar 标明 `synthetic` 与 `prototype_only`。不要把原始合同没有的标记字段塞进 DTO 对象。
4. 参数 W30 秒、S5 秒、L2 秒只是待验证起点，不是实测结论。每次运行保存输入文件、配置和结果。

## 先记住这些词

- `event_time`：测量发生的时间；`received_at`：程序收到消息的时间。网络延迟会让两者不同。
- W（窗口长度）：每次计算往回看多长时间，当前试用 30 秒。
- S（步长）：隔多长时间发布一次新窗口，当前试用 5 秒。相邻窗口可能重叠。
- L（迟到容忍）：窗口发布前最多等迟到数据多久，当前试用 2 秒。
- TTL（有效期）：一条状态可以被视为“新鲜”的最长时间；过期后要标未知。
- `trial_id`：一次独立操作实验的编号；一场实验产生的窗口都用同一个编号。
- `UNKNOWN`：证据不够时表示“不知道”，不等于“无人”或“没有水”。

## SP-03：先验证时间对齐和窗口

### 目标

相同输入和相同配置，每次都产生相同窗口结果；乱序、迟到、缺失或一路断流不能造成无限等待，也不能把未知值补成“正常”。

### 按步骤完成

1. 写 10–20 行小样例数据，包含 flow/water/presence 三路，并分别放入 `event_time`（设备事件时间）、`received_at`（本机接收时间）、`boot_id`、`seq`。文件或配套 README 显式标注 `prototype_only`。
2. 写最小窗口程序，参数化 `W=30s`、`S=5s`、`L=2s`；给程序注入时钟，避免测试依赖真实等待。
3. 手算并记录每个场景的预期结果，再编程实现。至少检查窗口 `(t-W, t]` 的左右边界、乱序数据、允许迟到数据、超过迟到阈值的数据、某一路沉默、观测 TTL 过期、设备重启和缺少可信事件时间。
4. 对照手算结果逐项比对程序输出。窗口应按超时发布，不能因为一条传感器沉默一直等；迟到数据需单独记录，不能悄悄回改已发布窗口。
5. 把每个例子固定为输入和期望输出，供他人一条命令重跑。

对照候选规范检查缺失规则：flow 缺失时 flow 数值特征应为 `null`；water 缺失时 `water_contact=null`；presence 缺失时 `presence_state=unknown` 且 `absence_after_flow_sec=null`；三源全缺失时 `data_coverage_ratio=0`。传感器沉默不能卡住窗口发布，过 TTL 的终态必须为 `unknown`。S01 样例中的特征数值只是字段示例，不可直接当作你的黄金预期值。

### 完成交付

- `README.md`：参数说明、运行方法和窗口边界定义。
- `src/`、`tests/`：对齐程序、注入时钟和自动化边界测试。
- `data/`：输入样例及人工预期输出；`evidence/`：程序实际输出和日志。
- `REPORT.md`：每个案例的预期/实际、异常、限制与结论。

建议本地验收命令：`python -m pytest spikes/SP-03/tests -q`。附上运行环境和真实测试输出。

## SP-04：SP-03 完成后比较规则与小模型

### 目标

检查现有特征和标注能否区分“有人正常用水”“可能无人流水”“水接触”和“无法判断”。实验只回答可行性，不承诺真实家庭准确率。

### 按步骤完成

1. 先和组长/M6 Owner 确认 4–6 个可操作的测试情景和独立真值。真值来自操作记录，例如“测试者离开后打开水龙头”，不能把模型自己的输出当标签。
2. 每次独立操作分配唯一 `trial_id`。同一个 trial 产生的多个重叠窗口必须全部留在同一数据集分区；先按 trial 分训练/验证，再生成或汇总窗口，避免相邻窗口泄漏。
3. 先做规则基线，再做一个简单决策树。保存使用的特征、规则阈值、模型版本和数据划分清单。
4. 报告每类样本数、混淆矩阵、Macro-F1、每类误报/召回、UNKNOWN/拒判比例和推理耗时。样本太少时明确写“不足以比较”，不要只报总体准确率。
5. 至少保留一个无法区分或关键传感器缺失的反例；系统应能输出 UNKNOWN，而不是硬猜有人/无人或把水浸当成情境分类。

### 完成交付

- `README.md`：数据如何采集/生成、如何运行评估。
- `data/`：独立 trial 操作真值、输入与版本信息；`src/`：规则、简单模型和评估脚本。
- `evidence/`：可复现的划分清单、混淆矩阵和指标原始结果。
- `REPORT.md`：样本数量、限制、规则与模型比较、是否建议继续 ML。

建议验收命令：`python -m pytest spikes/SP-04/tests -q`，再运行报告中的评估命令。规则没有输给 ML 时，建议保留规则；不要求为了“用 AI”而上线模型。
