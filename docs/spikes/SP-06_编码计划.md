# SP-06：SQLite 事务与 Outbox 技术 Spike

**Owner：C　状态：NOT_STARTED　范围：`prototype_only`**

## 目标与停止线

用最少代码验证三个高风险点：

1. 一个业务变更与它对应的 Transition、Outbox 记录在 SQLite 中同成同败。
2. 云端不可用或 worker 重启后，待发记录仍在，重试沿用稳定的 `message_id`。
3. 传输确认和业务接收确认分别记录，不互相推导。

本 Spike 只验证本地持久化和 Mock Cloud。它不实现 HTTP API、完整事件状态机、硬件采集、真实 IoTDA、通用消息队列、多目的地、分布式锁或生产级监控。契约仍待会签，原型只放在 `spikes/SP-06/`，不修改正式 Schema/DTO，也不合入 `edge/`。

交付的是工程可行性证据，不是 exactly-once 保证。云端调用与 SQLite 事务无法构成一个原子事务；原型按**至少一次投递**考虑，稳定消息 ID 供接收侧去重。

## 最小实现

建议限制为 3 个实现文件和 3 组测试；如代码仍然很短，可合并文件，不为目录结构拆模块。

```text
spikes/SP-06/
  README.md                 运行命令、原型边界、prototype_only 标记
  REPORT.md                 结论、环境、限制与交接
  spike.py                  SQLite schema、事务操作、Outbox worker、Mock 接口
  tests/
    test_transaction.py     成功提交、故障回滚、重复请求/版本冲突
    test_outbox.py          Mock 失败重试、稳定 ID、回执分层
    test_restart.py         关闭并重开数据库后的待发恢复
  evidence/                 命令输出和关键查询结果
```

只用 Python 标准库 `sqlite3` 和仓库已有 pytest；不新增生产依赖，不新增通用配置框架、ORM、迁移工具、异步框架或 Docker 服务。测试使用临时数据库，禁止真实凭据。

原型只需三张核心表：

- `events`：当前事件版本及本次验证所需最小状态。
- `transitions`：追加式变更记录，`(event_id, event_version)` 唯一。
- `outbox`：`transition_id`、稳定 `message_id`、目的地、状态、尝试次数、错误摘要及可选传输/业务回执；当前只测一个 `huawei_iotda` 目的地。

幂等键可先作为 transitions/outbox 操作的最小字段实现；只有测试证明必须独立存储，才加第四张表。不要为未实现的多租户、多目的地或查询场景预留结构。

## 实施顺序与验收

### 1. 一个原子写入函数

实现一个同步函数，接收固定输入，在单个 `BEGIN`/`COMMIT` 中完成：版本校验、更新 `events`、新增 `transitions`、新增 `outbox`。使用确定性故障注入点验证每类写入失败时整体回滚。SQLite 约束承担唯一性保护；不先构造通用仓储层。

**通过条件：** 成功时三类记录齐全、版本递增；任一写点抛错后没有半成品。

### 2. 最小幂等与并发检查

同一幂等键与同一输入重复提交，不新增 Transition/Outbox；同键不同输入或旧版本得到明确冲突。用两个独立 SQLite 连接竞争同一版本，验证数据库层最多一个更新成功。只验证这一种并发竞争，不做压力测试或多 worker 吞吐测试。

ACK 的完整 HTTP 语义、权限、物理清除和事件关闭规则留给 I-008/I-009；本 Spike 不实现这些业务流程。

### 3. 单进程 Mock Outbox worker

worker 每次只领取一条记录。Mock 只需提供成功、暂时失败、永久失败三种结果。验证状态路径 `PENDING → SENDING → ACCEPTED`、`SENDING → RETRY_WAIT` 及最终 `FAILED`；重试保持同一 `message_id`。重试间隔作为测试参数，不在 Spike 中决定生产策略。

传输回执只有在 Mock 返回对应确认时写入；业务回执仅由单独的测试输入触发。worker 不修改 Event 或 Transition。

**边界：** 单进程、单 worker；不实现租约、分布式调度、指数退避调参、重复回调竞态或第二目的地。

### 4. 重启恢复

先将记录持久化为待发或 `SENDING`，关闭数据库连接并创建新的 worker 实例，再验证记录可恢复、`message_id` 不变。报告明确这是“进程重建/数据库重开”验证，不声称覆盖断电、文件系统损坏或真实 WAN 故障。

### 5. 报告和交接

记录 Python/SQLite 版本、精确命令、真实测试数量、关键数据库状态、失败场景和限制。状态使用 `PASS`、`PARTIAL`、`FAIL` 或 `BLOCKED`。交给 I-008 的是原子写入、唯一约束和恢复证据；交给 SP-05/I-010 的是回执层级问题。Mock 结果不计为云端 Gate 通过。

## 最小验收清单

- [ ] Event、Transition、Outbox 成功时同事务提交。
- [ ] 对三个写入位置分别故障注入，失败均无部分提交。
- [ ] 重复输入不创建重复 Transition/Outbox；同键不同输入和旧版本有冲突结果。
- [ ] 两个 SQLite 连接竞争同一版本时最多一个成功。
- [ ] Mock 暂时失败时本地事务成功、Outbox 留存，后续可重试且 ID 稳定。
- [ ] 重开数据库和 worker 后能恢复待发记录。
- [ ] transport receipt 与 business receipt 分开；无业务回执时不伪造。

来源贯穿和 `simulation/mixed/unknown` 禁外发仍是正式 C4/CT15 要求，但本 Spike 没有真实外发器，也不实现来源策略；在报告列为 I-008/I-009 的后续验收项。真实 IoTDA 接入由 SP-05 处理。

## 推荐推进节奏

先评审测试矩阵与 SQLite 事务草图；随后完成阶段 1、2；通过后做 Mock worker 和重启恢复；最后报告并交接。任何阶段若需新增依赖、服务或抽象层，先说明它解决的具体验收失败，再决定是否加入。
