# 待机与观测文件竞态修复

## 已定位与尚未定位

原小时观测的两次长空档有独立Windows电源事件佐证：04:55:15Z至05:05:31Z约616秒，05:05:31Z至05:18:34Z约783秒，均为Modern Standby进入/退出。对应采样空档621.140和781.688秒；唤醒后的旧快照503符合时效保护。该证据能解释长空档，不能自动解释其余所有503。

电源事件仅保存UTC、事件ID及首行进入/退出描述，无完整设备事件载荷。

## 修复内容

1. runtime_endurance.py增加显式--keep-awake：只在本次观测的线程上请求ES_CONTINUOUS|ES_SYSTEM_REQUIRED，finally释放，不修改电源计划、不保持显示器常亮；不能阻止用户主动睡眠。API依据见Microsoft官方文档：https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate 。
2. 采样覆盖成为PASS必要条件：最大采样间隔不超过max(5秒,两倍配置interval)。即使采到的API均200，有大空档仍不通过。拒绝NaN/Infinity时长或间隔。
3. 新增长暂停恢复管线测试：旧快照过期时Unavailable，恢复不补造缺失观测，实际新窗口重新发布后可读。TTL与业务时间语义不变。
4. 首次900秒受控试验在189.141秒因FileNotFoundError结束；已有27个稳态样本均200，仍整体FAIL。扫描先列文件再stat，可能撞上原子发布临时文件或WAL回收；缺少堆栈，不能声明具体消失文件已确认。
5. 修复容量扫描：只统计正式JSON检查点；每个候选文件单次stat，消失文件计入transient_files_disappeared；权限等其他错误不吞掉。重现文件消失竞态并验证PermissionError仍失败。
6. 新增analyze_runtime_observation.py汇总状态、最大睡眠估计/推进耗时/调度空档及原始异常样本，不自动猜测根因。诊断请求晚于live请求，明确其非原子观测限制。
7. 已确认step重复验证同一检查点：事件gate/classify及投影gate/classify共四次恢复重算，另加保存时一次计算。新增ContextVar局部verification_scope，最多4项，仅在单次Simulation.publish中使用；每次restore仍读取文件并验证内容摘要，配置仍逐次检查，返回内容深复制，发布结束释放，不按路径或TTL跨窗口缓存。对照测试计算由5次降至2次，感知摘要一致；不据此宣称原503已全部修复。

## 最终结果

- 958764a受控基线900秒：实际901.625秒、176次采样、167个稳态样本全部live=200；max采样空档7.391秒（门槛10秒）、最大调度空档0.422秒、最大advance2.594秒、timer failures=0。最大睡眠估计增量约0.0145秒，属于计时量化级差异，不认为发生了显著睡眠。数据库完整性ok、重复OPEN=0、进程退出和端口关闭确认；PASS。
- db9e671优化版180秒：实际181.594秒、36次采样、27个稳态样本全部live=200；采样覆盖达标，数据库和退出检查通过；PASS。最大advance约0.703秒，但与基线时长及负载不同，不据此报告性能提升比例。
- 原始小时FAIL和189秒观测工具FAIL均保留。明确定位的是原长空档与Modern Standby相吻合，以及容量扫描的消失文件竞态；不能推断原全部11次503具有同一原因。
- 下一步用优化版固定提交在保持唤醒、无大采样空档的条件重跑完整一小时，再决定是否合并可靠性放行。当前代码已具备所需诊断和观测门槛；本轮不预填该结果。
