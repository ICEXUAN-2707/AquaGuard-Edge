# 调度与主机暂停诊断

## 当前在解决的问题

功能与人工验收已经证明页面和基本业务可用；当前可靠性阶段要验证持续运行时数据是否仍有效。过去一小时FAIL含11个live=503和约782秒采样空档，但缺少当时耗时和主机睡眠记录，无法事后确定根因。503表示拒绝过期证据的保护可能正常，health=200只证明存活，不能证明实时数据新鲜。

本轮目标是区分：业务step/tick计算或磁盘操作慢、清醒期间线程/事件循环调度空档、主机睡眠/休眠、UTC校时变化。没有调整TTL、测量时间、算法或事件策略。

## 代码与证据

- runtime_diagnostics.py记录cycle数量、失败数、最近成功UTC、最大推进耗时与调度空档、最近周期的step/tick/CPU耗时。不包含原始观测、路径或凭据；异常类型代替异常消息。
- run.py在advance两侧计时；耗时超过1秒、调度空档超过2秒或异常时将结构化记录写入本地服务日志。日志阈值仅用于诊断，不是正式SLA。CPU是服务进程CPU总量，不独占当前step。
- api.py新增受现有Bearer认证保护的GET /api/runtime/diagnostics，可按device_id查询快照captured_at/TTL/age；仅诊断，不修改业务状态。
- runtime_endurance.py增加UTC、单调时间、采样间隔/迟延、HTTP耗时和认证诊断快照。
- Windows另采集GetTickCount64（含睡眠）和QueryUnbiasedInterruptTime（只计清醒）；相邻差值估计睡眠增量，非Windows或查询失败明确为空。计时精度有限，极小正差不能直接判为睡眠，需结合显著时间差与日志。历史观测缺失该字段，不能倒推为已确认睡眠。

官方计时依据：https://learn.microsoft.com/en-us/windows/win32/sysinfo/interrupt-time

## 下一次503定位方法

1. 看projection.age是否超过TTL，保留错误样本与相邻诊断。
2. 若估计睡眠时间明显增加，优先检查主机休眠；若睡眠差值近0而gap大，排查清醒调度、进程停顿及资源竞争。
3. 若step或tick耗时大，分别分析分析/工件写入与SQLite计时，必要时再细化子阶段；CPU小但墙钟大只能提示等待，不能独断磁盘根因。
4. 若UTC与其他时钟差异突变，检查校时。多原因可能并存。
5. 控制环境后重跑一小时，保持原FAIL和标准不变；不能从两分钟PASS外推小时可靠性。

本轮完成可观测性和受控过期/恢复验证，原FAIL根因仍未证实。完整小时重跑应在诊断可用并明确环境条件后开展，不在报告中预填通过。
