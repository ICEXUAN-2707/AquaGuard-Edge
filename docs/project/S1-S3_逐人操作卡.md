# S1–S3逐人操作卡

首次安装软件或不熟悉终端时，先按[零基础软件安装与复现手册](零基础软件安装与复现手册.md)完成环境、窗口操作与对应分支复现，再回本页进行数据讨论和实物分工。

2026-11-03。配合[新人手册](新人分步推进手册.md)使用。命令均在仓库根目录的PowerShell运行。本文补执行细节，不新增实测结论；角色A/B/C沿用现有分工，复核人由组内指定，不能由操作员代签。

## 开始前：三人共同准备

1. 打开根README的“本地API基线”，确认自己处于仓库根目录：`Get-Location`。应能看到`edge`、`spikes`、`web`。
2. 检查环境：`Test-Path .\.venv-app\Scripts\python.exe`。不存在时按根README建立环境和安装锁定依赖；不要改用审计用的`.venv`猜着运行。
3. 各自建立一份执行记录：步骤ID、日期、提交号、实际命令、退出结果、输出路径、预期/实际、疑问、下一步。新结果使用新目录或数据库名，历史证据不要当作本次结果。
4. 角色交接：A提供原始观测及采集条件；B提供窗口、特征、情境及拒绝原因；C提供事务与事件需求，并检查两端语义是否能用于业务。

## S1-A：先理解一条消息如何产生

看文件顺序：

1. [SP-02 README](../../spikes/docs/A/SP-02/README.md)：读“当前实现”和根目录运行命令，先知道全部是simulation。
2. [线上协议](../../spikes/docs/A/SP-02/WIRE_PROTOCOL.md)：找Topic、设备身份与三种载荷定义。
3. `spikes/SP-02/src/cli.py`：搜索`generate`，了解生成命令输出什么，不要求通读全部代码。

先执行单元检查，再生成一批模拟消息；下面目录名每次换一个尚不存在的名字：

```powershell
.\.venv-app\Scripts\python.exe -m pytest spikes/SP-02/tests/unit -q
.\.venv-app\Scripts\python.exe spikes/SP-02/src/cli.py generate --directory spikes/SP-02/data/onboarding_A_20261103_01
Get-ChildItem spikes/SP-02/data/onboarding_A_20261103_01
```

为什么：先排除基础软件问题，再认识线上载荷；此步不依赖传感器或Broker。打开生成文件，各找水流、水接触、人体存在的一条，抄出字段、单位、来源、身份，按协议解释。不能自行认为线上载荷已经是B能直接读取的完整DTO。

交付：三条样例的文件位置、字段解释表、实际测试结果。完成程度：能说清三种数据差异，以及generate不证明通信或实物采集。

进阶通信由A按README部署本机Mosquitto；先检查`cli.py subscribe --help`、`publish --help`、`export --help`，再使用同一新实验目录。订阅端READY后才发布，订阅结束后用export导出accepted数据；保存实际参数和输出路径。没有Broker时标记该检查未执行，不妨碍先做S2阅读练习。README尾部含旧能力描述，涉及manual_ack、重连等以最新收尾报告和代码为准，出现矛盾记录后讨论。

## S1-B：从回放走到规则

依次打开[SP-03 README](../../spikes/docs/B/SP-03/阅读入口.md)、[M4 README](../../spikes/docs/B/SP-03-features/阅读入口.md)、[M5 README](../../spikes/docs/B/SP-04/阅读入口.md)，只读运行及输出说明。运行前先备份或记录已有输出的版本，以下演示会更新指定evidence文件。

```powershell
.\.venv-app\Scripts\python.exe spikes/SP-03/src/replay.py spikes/SP-03/data/synthetic.jsonl --output spikes/SP-03/evidence/onboarding_B_20261103_01.jsonl
.\.venv-app\Scripts\python.exe spikes/SP-03-features/demo.py
.\.venv-app\Scripts\python.exe spikes/SP-04/demo.py
.\.venv-app\Scripts\python.exe spikes/SP-04/evaluate.py
```

逐条执行，失败先停。打开这些文件：

|文件|具体看什么|为什么|
|---|---|---|
|`spikes/SP-03/data/synthetic.jsonl`|选一条输入，找测量与接收时间|认识原始观测|
|刚生成的onboarding回放文件|找同一观测的包装信息|理解回放不是实际等待，也不是完整窗口服务|
|`spikes/SP-03-features/evidence/r07_feature_windows.json`|选一个窗口，记录实际身份和特征字段|看到特征确实是什么|
|`spikes/SP-04/evidence/r03_assessments.json`|找对应窗口的情境、依据或拒判|区分观测与推断|
|`spikes/SP-04/evidence/r05/comparison.json`|读逐场景结果，找错误或限制|避免只看总分|

注意：第一条replay命令是早期独立回放练习，不自动成为后面demo的输入。M4/M5是否关联要根据实际窗口引用核对，不能把不同演示拼成同一链路。

交付：一份输入→窗口/特征→情境解释表，注明哪些文件实际关联、哪些只是独立示例。完成程度：能解释至少一个有效判断和一个拒判/限制；无需此时训练模型。复现检查按M5 README的回归命令执行一次，保存本次结果，不累计历史测试数量。

## S1-C：亲眼看见保存、重复和回滚

先读[SP-06人工指南](../../spikes/docs/C/SP-06/MANUAL_TEST_GUIDE.md)的准备及测试一。使用全新数据库路径：

```powershell
$onboardPython = '.\.venv-app\Scripts\python.exe'
$onboardRunner = 'spikes/SP-06/tests/manual_runner.py'
$onboardDb = 'spikes/SP-06/onboarding_C_20261103_01.sqlite'
Test-Path $onboardDb
& $onboardPython $onboardRunner init --db $onboardDb
& $onboardPython $onboardRunner submit --db $onboardDb --case open
& $onboardPython $onboardRunner inspect --db $onboardDb
& $onboardPython $onboardRunner submit --db $onboardDb --case replay_open
& $onboardPython $onboardRunner inspect --db $onboardDb
```

若Test-Path为True先换名。第一次应看到Event版本1、Transition和PENDING Outbox各一条；重放应显示replayed且行数不增加。为什么：理解一次业务变化如何保存、重复请求为何不能重复建记录。

继续按人工指南测试二、三、四，分别使用它要求的新数据库；每条命令执行后核对预期。冲突和故障注入预期报错，不能仅凭非零退出码判为产品失败。

交付：每个场景的命令、前后状态对照、实际结果。完成程度：能解释幂等、回滚、重试、稳定message_id，以及Mock不证明IoTDA已收到。请A或B照记录独立复核一项。

## S2：三人一起追踪数据，建议分两轮

### 第一轮：只看已有样例，不要求部署通信

A打开[候选契约](../../reference/reference_02/00_Contracts_V1.2_修订候选.md)的三源定义、线上协议及时间假设，选B的`synthetic.jsonl`中一条完整观测。A填写：observation_id、device、源、boot、seq、事件时间、接收时间、时间质量、来源、载荷、单位；名称以实际Schema为准，缺字段不得自行补造。

B核对这条观测在独立replay输出中的对应项，解释effective_time、degraded_time等包装信息；再独立选择M4/M5中实际关联的窗口示例，解释窗口范围、特征、质量门控及情境。不声称两套演示天然相连。

C问并记录六个问题：重发是否重复；同身份不同内容怎么办；设备重启怎样隔离；时间不可信怎么办；状态过期怎么办；人工确认能否清除物理异常。对照契约和[M3决策表](../../spikes/docs/B/SP-03/待确认口径表.md)记录答案出处，未决项保留，不代替会签。

### 第二轮：使用A实际导出的accepted数据

前置：A完成通信和export。A交唯一完整DTO及原始日志；B先打开`spikes/SP-02/src/handoff_b.py`及[AB第二轮核对](AB_第二轮交叉核对.md)，确认实际参数、输入要求与有限实验边界，再按文档执行交接。参数不清先用脚本`--help`核对，禁止拿原始received日志直接替代accepted DTO。

三人共同填表：输入文件/行或观测身份→接受或拒绝依据→实验及窗口引用→特征/质量→可验证的后续输出。没有接通的部分明确写未接通。

完成：每人能用自己的话解释相同样例；一条数据能用身份关联而非凭文件行号猜测；重启/过期/null不会被当正常值；争议有Owner和下一动作。交付文件由C归档，记录具体版本，Reviewer按实际复核填写。

## S3：把“硬件已到货”拆成可执行任务

主文档：[A零基础采集手册](../../spikes/docs/A/A_零基础实验与数据采集手册.md)。本节按其P01–P10、E00–E07执行，不另造实验口径。

|子步|A做什么、看哪里|B做什么|C做什么|完成到什么程度|
|---|---|---|---|---|
|S3-0资料|拍实物正反面与标签；按采购确认单核型号；收集匹配手册，逐项填P01–P04/P08|核对输出能否表达flow/contact/presence，列单位和未知状态问题|建立参数缺口表，指定电气复核人|型号、引脚、供电、输出电平和资料页码齐全，未知项明确|
|S3-1工具|按P05/P10确定工具链、固件、构建、烧录、采集和停止方法；缺驱动先建任务|提出需要保留的原始字段、时间与错误信息，检查日志样例|检查每条命令是否能由另一人复现，保留版本|有匹配板型的可执行操作卡和短试记录；未实现工具不能写已完成|
|S3-2准入|按E00断电核对接线、电平适配、水路与停止方案|核对数据采集方案，不代签电气结论|记录有经验复核人的结论和未决项|相应资料与复核齐全才进入通电；缺项停在本步|
|S3-3板卡|按E01运行基础固件，观察60秒，按核准方式重启5次|查boot变化、uptime、seq与时间可信度|独立记录重启动作，关联日志与版本|重启点可追溯，无身份异内容；未同步时间不伪装已同步|
|S3-4基线|按E02每次只启用一个源，保持无流/干态/无人各5分钟|检查有效、未知、错误及噪声，不把无脉冲视为在线证明|记录实际环境和干扰动作|有原始日志、动作标签、质量统计及限制|
|S3-5单源|水流按E03/E04；探头E05；雷达E06；一次只做一项|预先核对指标和阈值，事后从原始数据复算|担任动作记录或复核，不根据结果改变标签|标定和复测分开；阈值固定后独立验证，失败记录保留|
|S3-6故障|按E07批准的断开方法测试各源3轮|查超时、unknown及恢复，报告不可观测状态|记录故障起止及恢复，检查证据完整|能区分正常/未知/不可诊断；不能虚构失联能力|

### 一次实验的现场动作

1. C先给run/trial编号；A写设备、固件、标定、配置版本；B写预期及指标，先于采集确定。
2. A按已核准命令启动，C记录开始；三人先看30秒日志是否真正写入文件。无记录先停，不开始正式动作。
3. A操作，C独立标动作和真值；B观察数据质量。人员不足可以兼任，但最终由另一人复核。
4. A按已确定方法停止；C记录结束、异常及现场条件；B只在派生目录计算，不修改raw。
5. 共同对照E03–E07对应判据，记录PASS/PARTIAL/FAIL/BLOCKED或已采集待判定，阈值未定不能写精度PASS。

水流：记录初末脉冲、相同时段的体积与时长，按手册做3档各5次标定、各3次独立复测。B手算一条：K=N/V，Q=60N/(K×秒数)；说明量具与起止误差。探头：移水时刻与真正干燥时刻分记，不能混用。雷达：固定位置和配置，分别测无人、移动、自然静止，unknown单列。详细次数和操作以采集手册E03–E07为准。

### S3结束要交什么

参数/接线复核、工具命令与停止方法、设备/固件/配置版本、原始日志、独立动作标签、标定和复测表、派生指标、实际报告及复核意见。报告必须说明三源是否各自验证，不能因为一种传感器通过就整体通过。S3完成后再按S4做三源并发与B交接。

## 每轮讨论只回答四个问题

现在在哪个子步？证据在哪？最早阻塞是什么？下一次由谁交什么产物？不会描述时，把命令、完整错误、预期依据和最小输入放进新人手册的提问模板，避免只说“跑不了”。
